### 2.2 逐代为什么这么改

**v5 —— 布局与预算剪枝（单独用反而更差，但必要）**

- 把"中心 + 正六边形 r=1200"换成参数化的"中心 + 正 n 边形环"，并引入
  `scan_probe_limit`：某频道攒够 N 条读数就停止在后续扫描点重复测它。
- 引入**可证明安全的范围上界剪枝**：若当前检测点到该频道可行域的最小距离
  > 1500m（有效接收半径上界），则该次检测**必然** no_signal，可直接跳过。
  可行域必定含真值，所以这条剪枝不损失任何信息。
- ⚠️ 单独使用是 **369.64 s/源，劣于基线 332.19**。原因是 v5 仍然保留
  "先看 MEC≤20m 才清"的旧精定位流程，而剪枝省下的检测次数不足以补偿
  多绕的路。它的价值在于提供 `_scan_points()` / `_sweep_v5()` 基座，
  让 v6 之后的每一代都能在"可调布局 + 预算控制"上叠加。

**v6 —— 把两段路线合并成一条（结构杠杆最大）**

- 基线把行程切成两段互不相干的路线：覆盖扫描环（约 6889m）+ 扫描结束后
  逐频道清源（约 8020~9167m），两段相加 ≈ 14900~16000m。
- 但"7 个扫描点 ∪ 约 13 个待清源"一共只有约 20 个目标，一条 TSP ≈ 10000m。
  **两段分开走白白多花约 5000m（≈1000s 虚拟时间）**。
- v6 把 `scan(i)` 与 `clear(c)` 放进同一个任务集，每步取最近的任务执行。
  覆盖证书不受影响：所有扫描点仍会被访问，只是顺序由最近邻决定。
- 同时把 `schedule_min_readings` 设成 **1**：只要某频道有 1 条读数、估计点
  已知，就登记为待清任务。实测这一条是**最大的单项杠杆**（≈ −11%）：
  设成 2 会拖到扫描环走完才清源，破坏"顺路清"的交织（314.77 vs 267.19）。

**v7 —— 加前瞻（本仓库 mock 上略逊于 v6）**

- 纯最近邻短视：它不知道"先绕远一点、后面能连成一串"。v7 每一步对
  **整个待办任务集**求一条开放路径（NN 构造 + 2-opt 改进），只执行第一个任务。
- ⚠️ 本仓库 30 seed 实测 **325.20**，略逊于 v6 的 312.31；上游归档的 10 seed
  上两者为 326.05 / 321.05，同样略逊。保留它的理由是：v8/v9/v14 的调度骨架
  都建立在这个 2-opt 路由之上，且 `follow_plan=True`（批量规划）是明确负结果。

**v8 —— 直接清优先（问题3 的关键解锁点，问题4 的基类）**

- 观察：两条扫描读数（检测点相距约 1km、误差仅 ±1°）交会出的估计位置，
  与真值偏差**多数在 0~30m**，而清除判据是"清除点距真值 ≤20m"。
- 关键推理：**MEC > 20m 不等于估计点偏离 > 20m**——可行域可能是一条细长条，
  长轴几十米而质心几乎在真值上。基线却据此先去别处补读数，
  白白多走一趟（每源最多 250m 位移 + 一次 5s 检测）。
- 于是改成：走到估计点先 `/clear`（失败也仅 5s，与一次检测同价），
  失败才就地补一条读数再走常规精定位。**332.19 → 267.19（−19.6%）**。

**v15 —— no_signal 排除修正估计点（最终交付）**

- 数学依据：全向源在点 B 处 no_signal ⟹ `|B−G| > R ≥ 1000m`
  （附录2-2 有效接收半径下界），即真值必在 `disk(B, 1000)` **之外**。
  基线只用 direction 读数（楔形 ∩ 1500m 圆盘），完全没用这批排除信息。
- v15 记录每频道的 no_signal 检测点，估计时在保守可行域上网格采样、
  剔除落入排除圆盘的样本、取幸存样本质心。**可行域本身不变**（MEC≤20m 判据
  仍用原保守域），只是让调度锚点与直接清的命中点更准。
- 另外补了在线 or-opt（段长 1–3 搬家），与 v7 的 2-opt 配套。

### 2.3 ⚠️ v15 的两个必须写清楚的实测事实

这两个事实与 `国赛B题工程文件` 的会话记录**不一致**，以本仓库 mock 的实测为准：

**(a) 归档表格里的 or-opt 是"空操作"，而且原因是实现 bug（2026-09-13 复核发现）。**

| 臂 | 全清 | avg 中位 | 路程中位 |
| --- | ---: | ---: | ---: |
| `v8`（基线） | 30/30 | 267.19 | 13136 |
| `v15 or_opt=4, excl=on`（**旧实现，有 bug**） | 30/30 | 273.73 | 13288 |
| `v15 or_opt=0, excl=on` | 30/30 | 273.73 | 13288 |
| `v15 or_opt=4, excl=off`（**旧实现，有 bug**） | 30/30 | **267.19** | **13136** |
| `v15 or_opt=0, excl=off` | 30/30 | **267.19** | **13136** |

`or_opt_passes` 取 0 或 4，结果**逐位相同**。归档据此写过"or-opt 在线版 ≈ 0"，
但 2026-09-13 的独立复核 (`review_20260913/审阅结论.md` §5) 查明这**不是**中性的
证据，而是**比较基准写错**：原实现在搬移一个片段后，用

```python
base = self._path_len(start, rest)      # rest = 删除该片段后的路线
if self._path_len(start, cand) < base - 1e-9:   # cand = 片段插回后的路线
```

即**拿"删掉片段后的路线长度"当基准，与"片段重新插回后的路线长度"比较**。
由三角不等式，插入一个非退化片段不会让路线更短（除非插入到原位），
因此该判据**几乎永远不成立** ⟹ 循环空转，or-opt 是 no-op。

**现状**：该 bug 已在 `strategy_v15.py` 修正（基准改为**本轮搬移前的完整
`route`**：`base = self._path_len(start, route)`）。

**并且交付配置随之改为开启**：`versioned.OR_OPT_PASSES` 由 `0` 改成 **`4`**。
原先设 0 的唯一理由就是"归档里 or-opt 在线版 ≈ 0，属中性项，不要把中性项当收益
写进论文"——既然那个"中性"是实现 bug 的假象，这个理由不再成立。

修正后的实测（本仓库 `script/q3_or_opt_ablation.py`，三个种子集，均 100% 全清）：

⚠️ **两件事必须分开**（`script/q3_or_opt_ablation.py` 就是为它们写的）：

1. **扫描布局定稿（6/1130/3）是问题3 最大的一项收益**（约 −4.5 ~ −8.6 s/源）。
   上一版注册表只覆盖了 `schedule_min_readings` / `or_opt_passes`，扫描布局一直沿用
   `Q3V5Params` 的字段默认 `7/1110/2`，而最终工程副本的 `FINAL_PARAMS` 是 `6/1130/3`。
   判别依据：归档口径 + `or_opt=0` 时定稿布局在 seed 1–30 上给出 **264.81**，
   与最终工程 `README` 的 v15 数字**逐位一致**。现已并入 `versioned.Q3_SCAN_PARAMS`。
2. **覆盖式清除在问题3 上是中性的**（±0.5 s/源，噪声内）。`q3-v18` 之所以是问题3

### 3.2 逐代为什么这么改

**v8 直接套用 —— 反例：发现层必须朝向完备**

全向源的覆盖判据是"圆盘覆盖"（任一点到最近停点 ≤ 1000m）。定向源只在
**正面半平面**内有信号，于是圆盘覆盖 **≠** 发现保证：源可以落在某停点的
有效接收半径内，却因为朝向背对而收不到（实测 seed 7 频道 2：距离 438m、
夹角 94.1°）。完备性条件是

    对任意位置 G 与朝向 φ，存在被访问节点 p 使 |p−G| ≤ 1000 且 (p−G)·u(φ) > 0。

由"源恰好位于某停点上、朝向背离所有邻居"这一最坏情形可推出
**节点间距必须 ≤ 1000m**。7 点环（弦长 >1000m）不满足，因此大量漏清。

**v9 —— 朝向完备的两圈式发现层 + 正面锥（阶段性有益尝试）**

- 发现层：论文的轴向三角网格 s=950 是 31 点、最坏正面距离 946.06m、
  行程 28500m，而且该点集上 NN+2-opt 的压缩量为 **0**（已是 TSP 最优），
  即"固定点集内再优化顺序没有空间"。要省只能改点集。
- 两圈式：内圈铺间距 ≤1000m 的三角网格（`s=950, r≤1750`）+ 外圈一圈
  12 点（`r=1900`，弦长 983m ≤ 1000m，专管"贴边朝外的源"）。
  结果是 **25 点、18828m**，最坏正面距离仍 ≤1000m，**行程 −34%**。
- 精定位：基线打分里的 `sep_weight`（追求角度分离）会把候选点推到
  "与已有读数方位差最大"的方向——对定向源那正是**背面**，测了必然
  no_signal、可行域不收缩，流程在同一侧反复空转（`_diag_v9b` 实测：
  单信道烧掉 51~127 次检测仍漏清）。v9 把候选点限制在
  "估计点 → 最近一次成功检测点"方向 ±`front_cone_deg` 的正面锥内。
- 另加两处退路：可行域"长条"时沿最长弦在**可行域内部**取点（长条内任一点
  到真值 ≤ 直径，且基本在正面侧，几乎必出读数）；落空后把候选点关于估计点
  **镜像**到另一侧再测一次。
- ⚠️ **仍然会漏清**：楔形退化几何下这些补救探点全都落在源的背面。
  归档 10 seed：546.28 s/源，8/10 全清。

**v14 —— 沿射线推进（上一代交付；现冻结为对照臂）**

- **正确性级修复（walk-the-ray）**：设 A 为最近一次成功读数的顶点，u 为该读数
  的示向单位向量，源 `G = A + t_G·u + ε`。射线上的点 `q(t) = A + t·u`：
  - `t < t_G`：`q−G` 与 `A−G` 同向 ⟹ 落在源的正面半平面；且 `|q−G| ≤ |A−G| ≤ R`
    ⟹ **必出读数**；
  - `t > t_G`：`(q−G)·u(φ) = (t−t_G)(u·u(φ)) < 0` ⟹ 背面 ⟹ 定向源**必 no_signal**。
  于是"步进 + no_signal 二分回退"在 O(log) 步内把源距压到小区间。对全向源
  同样安全（no_signal ⟺ 越过 R，仍是上界）。
  > ⚠️ **该论证不成立（2026-09-13 复核）**：测向有 ±1° 误差，靠近波束边缘时机器狗
  > 可能在**尚未接近源之前就走到背面** —— 此时 `no_signal` 是"超出接收半径 ∪ 落在
  > 波束背面"的**析取**，不能推出"已越过真源"，因此 `hi = t` 的截断不成立。
  > 复核给出显式反例：A=(0,0)、G=(1000,0)、接收半径 1200m、源定向 90.1°；
  > 若读数偏移为 −1°，沿该读数走 450m 得 q≈(449.93, −7.85)，距源仍约 550m 却已在背面。
  > 因此**射线推进只能当启发式，不能作为"必清"的证明，也不能污染保守可行域**
  > （`q4-v18` 改用与朝向无关的 20m 失败清除圆 + 25m 格覆盖，见 §3.5）。
- **区间平移继承**（seed 7 靠它救回）：direction 读数后顶点前移时，距离区间按
  `[lo−t−δ, hi−t+δ]`（δ = 0.05t + 10，覆盖 ±1° 量化与新旧射线方向差）
  **平移继承而非重置**。修复前：近平行楔形狭缝每次重置 `lo=0, hi=∞`，
  二分从零开始，12 步耗尽仍差 8m（near 要求 ≤5m 且在正面，差 8m 即听不到）。
- **地毯式清除**：区间坍缩 <40m 时，在 `[lo,hi]` 的 0.5/0.2/0.8 分位连发
  `/clear`。依据是**清除判据（≤20m）与朝向无关**，区间内任一点到最近分位点
  ≤ 0.3×区间长 + 横向 ε < 20m，必命中。
  > 前提是**该区间没有被错误的 `no_signal` 截断**：一旦上界被射线启发式错误收缩，
  > 整个区间都可能落在真值之外 —— 这正是 v14/v17 在持有集漏清的机制，
  > 也是 `q4-v18` 必须补"覆盖兜底"的原因。
- **同点免重测 / 失败点免重清**：确定性误差下同一 `(频道, 检测点)` 的读数与
  清除结果不变，重复是纯浪费（v9 失败种子里同一批点被反复测 4+ 遍）。
- **规模效应**：v9 在 30 seed 上 526.30 s/源但只有 26/30 全清；v14 全清 30/30。
- **泛化（2026-09-13 补充）**：这一血脉在**持有集 61–160** 上并不全清 ——
  复核用 v14 的最优参数（`schedule_min_readings=2, scan_probe_limit=2`）测 v17 时得到
  默认混合 **97/100**（见 §3.5）。即"30/30 不等于全清保证"，这是该结论的最早证据。

### 3.5 v17 → v18：为什么上一代交付被降级（2026-09-13 复核）

### 3.5.1 触发事件：调参种子上全清 ≠ 全清

`q4-v17`（方法二 24 点联合优化布局 + 15m 环形兜底）在**调参用过的 60 个种子
（1–60）**上是 **760/760 全清、vt 中位 6242.8 s**，看起来比 v14 更好。
但独立复核 `review_20260913/` 换用**从未参与调参的持有集 61–160** 重跑，结论反转：

| 场景（种子 61–160） | v17 全清局数 | v17 清除源数 | 加"区域覆盖兜底"后 |
| --- | ---: | ---: | --- |
| 默认混合分布 | **97/100** | 1280/1283 | 100/100、1283/1283 |
| 全定向压力场景 | **97/100** | 1279/1283 | 100/100、1283/1283 |
| （对照）Q3 全向 | 100/100 | 1283/1283 | 100/100、1283/1283 |
| 后续验证集 161–260（仅覆盖版） | — | — | 100/100、1299/1299（两场景各） |

> 上表数字取自本工作区 `review_20260913/` 的复现日志（`mixed.log`、
> `all_directional.log`、`mixed_cover.log`、`all_directional_cover.log`、

漏清的 6 例是：混合 seed 80/ch19、88/ch3、137/ch14；
全定向 seed 77/ch8、128/ch7 与 ch11、140/ch14。**这些源全部已有测向读数，
没有"从未发现"的源**——即问题不在发现层布局，而在精定位与清除兜底。

两条根因（也就是 v18 要修的两条）：

1. **射线推进不是证明。** `_walk_the_ray` 在 `no_signal` 后直接 `hi = t`，
   其正确性依赖"读数射线穿过真源"。测向有 ±1° 误差，在波束边缘附近机器狗可能
   **还没接近源就已经走到背面**（复核给出显式反例，见
   `framework/src/mathmodel2026b/versioned.py` 中 `q4-v14` 条目与本文件 §3.2）。
2. **环形试清不是覆盖。** "中心 + 半径 15m 的六点环"对任意误差方向只保证覆盖到
   `15cos30° + √(20² − 15²sin²30°) ≈ 31.53m`，盖不住 35–40m 的估计误差；
   单纯加大环半径还会在环间留空隙。

**降级结论**：`q4-v17` 保留为**冻结对照臂**（`INTERMEDIATE_ENTRIES[4]`），
不再作为问题4 的交付入口。它是"在调参种子上全清 ≠ 全清"这条教训的活证据。

### 3.5.2 `q4-v18`：交付版新增的三层

`q4-v18 = q4-v17 的在线机制 + 下面三层`，三层都来自"知识矩阵"这条独立路线，
且都有充分性论证（代码与论证见 `framework/src/mathmodel2026b/strategy_v18.py`）。

**(1) 知识矩阵负例：失败 `/clear` 的 20 m 排除圆**

`/clear` 返回"未发现" ⟹ 以**清除点为心的 20m 闭圆盘内没有该频道的源**（附件1 §2.3）。
这条负例**与源的朝向无关**（光学/激光判据），对定向源同样严格成立 ——
比迭代版原先唯一可用的 `no_signal`（定向时是"超半径 ∪ 落在背面"的**析取**）强得多。
格完全落入某个排除圆时即可**安全丢弃**（若格的四角都在圆内，由范数凸性整格都在圆内）。

**(2) 可证明的覆盖式清除（`region_clear_plan`）**

把保守可行域 `F` 用边长 **25m** 的格铺开：格心到格内任意点至多 `25/√2 = 17.678m < 20m`，
因此"依次清除所有与 `F` 相交的格心"在**完整执行**时**保证**命中真值 ——
这是充分条件（计划带 `guaranteed` 字段），不是启发式；只在预算中断或格心不可达时失效。

**(3) 代价模型：两次 clear 可能比"再测一次 + 清一次"更便宜**

按修正后的计时（失败 `/clear` = 3s、成功 = 5s；`/measure` = 5s，另加换频道 1s）：

| 覆盖格数 k | 覆盖计划固定耗时 | 一次 measure + 一次 clear |
| ---: | ---: | ---: |
| 1 | 5 s | 11 s |
| 2 | 8 s | 11 s |
| 3 | 11 s | 11 s |

即 **k ≤ 2 时计划固定耗时严格占优（`3k+2` vs 11）且带覆盖保证**；k = 3 打平，由路程决定。
所以 v18 在走"直接清 / 射线推进"之前先算一遍覆盖计划，划算就直接执行。

**(4) 实测效果与代价**

- 持有集 61–160：混合与全定向两场景各 **100/100 局、源全清**（修复 v17 的 6 例漏清），
  代价约 **+0.4~2.6 s/局**；161–260 两场景各 100/100 局、1299/1299 源。
- ⚠️ **这是条件性保证**：前提是"真值 ∈ F"（F 由保守可行域给出）且预算未耗尽；
  计划被完整执行却没命中时策略记 `region_violated`，说明前提被证伪。
  **有限仿真全清不等于对所有案例的概率 1 保证。**

## 5. 移植到 Python 3.13 时必须修的一个坑

`@dataclass(slots=True)` 会为子类**重建类对象**，导致零参 `super()` 依赖的
`__class__` 单元格指向**原始**类。于是 `Q3V8Params` 实例在 `Q3V5Params`
的方法里调用 `super()` 时会抛：

```text
TypeError: super(type, obj): obj (instance of Q3V8Params)
           is not an instance or subtype of type (Q3V5Params)
```

CPython 文档的 `dataclasses` 章节对此有明确警告。上游归档在 Python 3.12/Windows
上跑，所以没有暴露。本仓库把 `strategy_v5/v6/v7/v8/v9/v14/v15.py` 里所有
零参 `super()` 改成**显式两参** `super(<定义它的类>, self)`，并在每个文件
顶部加了 `NOTE(端口适配)` 说明。

另有两处顺手修的健壮性问题：

1. `Q3V6Strategy.schedule_log` / `dist_by_kind` 原先只在 `run()` 里赋值，
   而 `diagnostics()` 可能在 run 之前被调用（runner 写 meta、单测断言）
   → 移到 `__init__` 初始化。
2. `script/run.py` 的 `--param` 合法性校验原先只看 `params.__slots__`，
   而 slotted 子类的 `__slots__` **只含自己声明的字段**，继承字段
   （如 `Q3V15Params.schedule_min_readings` 来自 `Q3V8Params`）会被误判为
   "未知参数" → 改用 `dataclasses.fields()` 递归收集。

   线上每场是随机案例（`case_code` 不同），跨场次只能算弱信号。
   要比较某条路线是否可用于正式测试，必须先补齐其在官方模拟器上的场次，并记录 `case_code`。
3. **环境相关的结论并列标注**。凡是"归档 mock"与"本仓库 mock"结论相反的
   （目前只有 v15 的 no_signal 排除项），一律在 `versioned.py` 的 `effect` 字段、
   `_bench_versions.py` 与本文档**同时标注两个数字**，不允许只留一个。
4. **计时口径必须标明**。失败 `/clear` = 3s、成功 = 5s、且 `/clear` 不切换频道
   （附件1 §2.3）；`legacy_clear_timing=True` 才能复现 2026-09-13 之前的归档数字
   （见 §3.6）。**引用任何基准数字时必须注明用的是哪一套计时**，
   禁止把两套口径的数字放进同一张论文表格。
